Detailed Explanation of weather_api_db.py and weather_scheduler.py
===============================================================

This document explains both Python scripts line-by-line and concept-by-concept in a way that anyone with basic Python knowledge can understand. Each numbered section corresponds to a logical block in the code and gives a plain-language description, purpose, and any important details or gotchas.

--------------------------------------------------------------------------------
FILE: weather_api_db.py
Purpose: Fetch current weather from OpenWeatherMap, parse the JSON response, and store selected fields into a MySQL database using SQLAlchemy.
--------------------------------------------------------------------------------

1) Load environment and libraries
---------------------------------
from dotenv import load_dotenv
import os
import requests
from sqlalchemy import create_engine, Column, Integer, String, Float, DateTime, func
from sqlalchemy.orm import declarative_base, sessionmaker
from sqlalchemy.exc import SQLAlchemyError
from datetime import datetime

Explanation:
- load_dotenv: reads key/value pairs from a .env file (like .env.weather) into environment variables so the script can securely read API keys and DB credentials.
- os: used to read environment variables.
- requests: sends HTTP GET requests to the weather API.
- SQLAlchemy imports: define the ORM model, create the engine, and manage database sessions.
- SQLAlchemyError: used to catch DB-related exceptions.
- datetime: for readable timestamps when printing or logging.

Common gotcha:
- You must install dependencies (requests, python-dotenv, SQLAlchemy, pymysql) in your environment.

2) Read configuration values
----------------------------
WEATHER_API = os.getenv("WEATHER_API") or os.getenv("weather_api") or os.getenv("WEATHER_API_KEY")
LOCATION = os.getenv("LOCATION") or os.getenv("location") or "Chennai"

DB_USER = os.getenv("DB_USER")
DB_PASSWORD = os.getenv("DB_PASSWORD")
DB_HOST = os.getenv("DB_HOST")
DB_PORT = os.getenv("DB_PORT")
DB_NAME = os.getenv("DB_NAME")
MYSQL_URL = os.getenv("MYSQL_URL") or None

Explanation:
- The script reads API keys and DB connection pieces from environment variables.
- Fallbacks are used so different variable names still work.
- LOCATION defaults to 'Chennai' if nothing is provided.
- MYSQL_URL: if present, is used directly (preferred). Otherwise the script builds a connection URL from DB_* pieces.

Important:
- If you use Railway, make sure you use the *public* host and port (not mysql.railway.internal).
- The SQLAlchemy URL must start with mysql+pymysql:// to use PyMySQL driver.

3) Construct SQLAlchemy DB URL
------------------------------
if not MYSQL_URL:
    MYSQL_URL = f"mysql+pymysql://{DB_USER}:{DB_PASSWORD}@{DB_HOST}:{DB_PORT}/{DB_NAME}"

Explanation:
- If you didn't provide MYSQL_URL directly, the script constructs it in the format SQLAlchemy expects, using the PyMySQL driver.
- This URL tells SQLAlchemy how to connect to your MySQL server.

Gotcha:
- Using mysql:// without +pymysql will prompt SQLAlchemy to use the MySQLdb driver, which may not be available or compatible, especially on Windows.

4) Define ORM model and engine
------------------------------
Base = declarative_base()

class Weather(Base):
    __tablename__ = "weather_data"
    id = Column(Integer, primary_key=True, autoincrement=True)
    city = Column(String(100), nullable=False)
    temperature = Column(Float)
    humidity = Column(Float)
    description = Column(String(255))
    timestamp = Column(DateTime, server_default=func.now(), nullable=False)

engine = create_engine(MYSQL_URL, pool_pre_ping=True)
SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)

Explanation:
- declarative_base(): base class for ORM models.
- Weather class: defines the table schema via Python class attributes.
  - __tablename__: the database table name.
  - Columns: id, city, temperature, humidity, description, timestamp.
- engine: the SQLAlchemy Engine that manages connections.
- pool_pre_ping=True: instructs SQLAlchemy to check (ping) connections before using them to avoid stale-connection errors.
- SessionLocal: factory to create database sessions (transactions).

Important:
- Base.metadata.create_all(engine) will create the table if it does not exist yet.

5) Create tables
----------------
Base.metadata.create_all(engine)

Explanation:
- This inspects all models attached to Base and creates missing tables in the connected database.
- Safe to run repeatedly; it will not overwrite existing tables.

6) get_weather_data(city) — fetch and parse the API response
-----------------------------------------------------------
- Build params with q (city), appid (API key), units=metric
- Send requests.get(BASE_URL, params=params, timeout=10)
- resp.raise_for_status() raises an error for non-200 responses
- Parse JSON: data = resp.json()
- Extract fields:
    city_name = data.get("name")
    main = data.get("main", {})
    weather_list = data.get("weather") or [{}]
    temperature = main.get("temp")
    humidity = main.get("humidity")
    description = weather_list[0].get("description")

Explanation:
- Uses a short timeout so the script won't hang forever.
- Uses metrics units to get Celsius.
- Validates presence of expected fields; returns None if critical fields are missing.

7) insert_weather_record(record)
--------------------------------
- Opens a session: session = SessionLocal()
- Creates Weather(...) object and adds it
- session.commit() to persist
- Catches SQLAlchemyError and does session.rollback() on failure
- session.close() in finally block

Explanation:
- Each insert uses its own session to ensure isolation.
- Proper error handling avoids leaving transactions open.

8) fetch_and_store_weather(city=None)
-------------------------------------
- Uses LOCATION default if city is None
- Calls get_weather_data and insert_weather_record
- Returns True on success, False on failure

Explanation:
- This wrapper is a single entry point the scheduler or GitHub Actions can call.
- It hides internals and returns a simple boolean for success/failure checks.

9) If file run directly (main guard)
------------------------------------
if __name__ == "__main__":
    ok = fetch_and_store_weather()
    print result message

Explanation:
- Running weather_api_db.py directly will perform a one-shot fetch+insert. Useful for debugging.

FILE: weather_scheduler.py
Purpose: Schedule fetch_and_store_weather to run automatically at specific times (morning, evening, night) using APScheduler.
--------------------------------------------------------------------------------

1) Ensure package imports and path
----------------------------------
import os
import sys
import logging
sys.path.append(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))

Explanation:
- The sys.path.append line ensures that when you run this script from inside the scripts folder (or by IDE), Python can find the 'scripts' package at the project root. Running from the project root makes this unnecessary, but keeping it makes running in IDEs tolerant.

2) Imports relevant to scheduling
---------------------------------
from apscheduler.schedulers.blocking import BlockingScheduler
from apscheduler.triggers.cron import CronTrigger
import pytz
from scripts.weather_api_db import fetch_and_store_weather, LOCATION

Explanation:
- BlockingScheduler: a scheduler that runs in the foreground and blocks the main thread with a loop.
- CronTrigger: schedule jobs with cron-like specification (hour, minute, day).
- pytz: timezone support; ensures scheduling uses IST (Asia/Kolkata) instead of server/runner default timezone.
- fetch_and_store_weather: the one-shot function from weather_api_db that fetches and inserts a record.
- LOCATION: default city imported so the scheduler knows which city to fetch.

3) Configure logging
--------------------
logging.basicConfig(level=logging.INFO, format="%(asctime)s [%(levelname)s] %(message)s")
logger = logging.getLogger(__name__)

Explanation:
- Basic logging prints timestamps and levels, which helps track job runs when looking at console logs or GitHub Actions output.

4) Define job()
---------------
def job():
    logger.info("Job started: fetching weather for %s", LOCATION)
    success = fetch_and_store_weather(LOCATION)
    if success:
        logger.info("Job succeeded.")
    else:
        logger.error("Job failed. Check logs for details.")

Explanation:
- Single responsibility: job triggers the fetch+store wrapper and logs the outcome.
- Keeps scheduling logic separate from business logic.

5) Setup scheduler and add jobs
-------------------------------
scheduler = BlockingScheduler(timezone=IST)
scheduler.add_job(job, CronTrigger(hour=7, minute=0, timezone=IST), id="morning_job")
scheduler.add_job(job, CronTrigger(hour=18, minute=0, timezone=IST), id="evening_job")
scheduler.add_job(job, CronTrigger(hour=23, minute=0, timezone=IST), id="night_job")

Explanation:
- Create a BlockingScheduler with IST timezone so triggers fire at local India time.
- Each add_job registers the same job at different times (07:00, 18:00, 23:00 IST).
- Using the same function avoids code duplication.

6) Start the scheduler
----------------------
try:
    scheduler.start()
except (KeyboardInterrupt, SystemExit):
    logger.info("Scheduler stopped by user.")
except Exception as e:
    logger.exception("Scheduler crashed: %s", e)

Explanation:
- scheduler.start() blocks and runs indefinitely until interrupted.
- Handles graceful shutdown on Ctrl+C and logs unexpected exceptions.

RUNNING & TESTING

   - Activate virtualenv: .venv\Scripts\activate  (Windows) or source .venv/bin/activate (Linux/Mac)

   - Add Railway/DB credentials and WEATHER_API as repository secrets.

--------------------------------------------------------------------------------
COMMON ERRORS & TROUBLESHOOTING
--------------------------------------------------------------------------------
1) ModuleNotFoundError: No module named 'scripts'
   - Cause: you ran script from inside the scripts folder (cwd wrong). Run from project root or use sys.path fix in scheduler.

2) Circular import / ImportError: partially initialized module
   - Cause: importing from each other (scheduler importing a function that imports scheduler). Solution: keep business logic (fetch+insert) in weather_api_db, scheduler imports only that function.

3) Can't connect to MySQL server / timed out
   - Cause: using internal host like mysql.railway.internal or wrong port. Use Railway's PUBLIC connection (containers-xxx.railway.app and the given port).
   - Also ensure firewall/ISP allows outbound connections to that port.

4) ModuleNotFoundError: MySQLdb
   - Cause: SQLAlchemy chosen MySQLdb driver because URL was mysql://... . Use mysql+pymysql://... and pip install pymysql.

5) API errors (401 Unauthorized / 404 city not found)
   - 401: invalid API key — check WEATHER_API value.
   - 404: city name misspelled — check LOCATION value.

--------------------------------------------------------------------------------
SECURITY & GOOD PRACTICES
--------------------------------------------------------------------------------
- Do NOT commit .env.weather to git. Add .env* to .gitignore.
- Use GitHub Secrets for production automation; never store secrets in repo files.
- Use connection pooling settings on engine (pool_pre_ping=True) to avoid stale connections.
- Add logging and alerting for production reliability.
